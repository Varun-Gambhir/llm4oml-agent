# Implementation and Methodology Context for Paper

## Intended Paper Frame

This paper should first be framed as a methodology paper, not as a results-first system report.
The central problem is:

> Large language models can produce plausible mathematical convergence proofs, but their mistakes are often local, structured, and non-monotonic across correction rounds. We need a way to evaluate and guide proof correction at the level of proof steps, not only at the level of final pass/fail correctness.

The implementation is an answer to that problem:

- A prover generates and revises convergence proofs.
- A judge or judge ensemble audits proofs at step level.
- The system tracks error transitions across iterations.
- RACS scores whether a correction was actually useful.
- Multi-judge evaluation improves trust in the feedback signal before it is used to guide the next proof.

## Core System Pipeline

The pipeline is implemented as a stateful LangGraph workflow.

1. **Input task**
   - The user provides an optimization algorithm description.
   - The task also includes assumptions such as convexity, smoothness, PL condition, bounded gradients, stochastic unbiasedness, or variance bounds.

2. **Initial proof generation**
   - The prover LLM receives a structured prompt asking for:
     - formal algorithm description
     - assumptions
     - theorem statement
     - step-by-step convergence proof
     - explicit `[Step N]` annotations
   - The step annotations are important because later evaluation must point to exact proof locations.

3. **Evaluation**
   - A judge LLM reviews the proof using a strict JSON schema.
   - The judge returns both coarse verdicts and granular error sets.
   - The main error categories are:
     - hallucination or unjustified claim
     - missing derivation step
     - operator or algebraic error
     - assumption misuse or assumption violation

4. **Correction**
   - If the proof does not pass, the prover receives the previous proof and judge feedback.
   - The correction prompt asks the prover to preserve correct material while fixing only the flagged issues.

5. **Verification**
   - The corrected proof is evaluated again.
   - The system compares previous and current error sets.
   - RACS is computed from the transition.

6. **Termination**
   - The workflow stops if the proof receives a passing verdict or if the maximum number of iterations is reached.

Relevant implementation files:

- `src/graph/workflow.py`: workflow orchestration.
- `src/graph/nodes.py`: prover and evaluator nodes.
- `src/agents/prover_agent.py`: proof generation and correction.
- `src/evaluators/single_judge.py`: single structured evaluator.
- `src/evaluators/multi_judge.py`: multi-judge consensus.
- `src/metrics/correction_metrics.py`: RACS computation.
- `src/metrics/judge_metrics.py`: JRS.
- `src/utils/prompts.py`: generation, evaluation, correction, and verification prompts.

## Why the Pipeline Is Designed This Way

### Why separate prover and judge?

A single LLM asked to both generate and verify its own proof can reinforce its own mistaken assumptions.
The implementation separates roles:

- The **prover** is allowed to be constructive and exploratory.
- The **judge** is forced to be conservative, structured, and deterministic.

This separation matches mathematical practice: proof writing and proof reviewing are different cognitive tasks.
It also makes the system easier to instrument because judge output becomes a structured measurement signal.

### Why use phase-aware temperatures?

The workflow uses different temperatures for different phases:

- generation: higher, to allow proof-path exploration
- correction: moderate, to avoid unnecessary rewriting
- evaluation/verification: near-zero, to stabilize JSON output and reduce inconsistent judgments

The reason is that creativity is useful when constructing a proof, but harmful when auditing one.
Evaluation needs consistency more than diversity.

### Why require `[Step N]` annotations?

Without step IDs, feedback becomes vague: "the proof has a gap" is hard to repair and hard to measure.
With step IDs, each error can be treated as a member of an error set.

This enables:

- targeted feedback
- correction tracking
- regression detection
- judge agreement measurement
- granular metrics without formal theorem proving

## Formal Problem Definition

The paper can formalize iterative proof correction as a discrete state-space trajectory.

Let:

- `P_0` be the initial proof generated by the prover.
- `P_i` be the proof after correction round `i`.
- `E_i` be the structured evaluator error set for `P_i`.
- `F_i` be the set of proof steps flagged for targeted repair after evaluating `P_i`.
- `I_max` be the maximum number of allowed correction iterations.

Each correction round is a transition:

```text
P_i -> P_{i+1}
```

The key object of study is not only the final proof `P_final`, but the transition behavior between proof states.
This is what makes the work different from standard final-answer evaluation.

### Correction Transition Categories

For two consecutive error sets, `E_prev` and `E_curr`, every correction transition can be analyzed through four categories:

1. **Fixed errors**
   - Errors present before but absent after correction.
   - Set form: `E_prev \ E_curr`.

2. **Persistent errors**
   - Errors that remain unresolved after correction.
   - Set form: `E_prev intersection E_curr`.

3. **Regressed errors**
   - New errors introduced during correction.
   - Set form: `E_curr \ E_prev`.

4. **Mixed transition**
   - A correction round that fixes at least one old error while introducing at least one new error.
   - This is important because LLM proof repair is often locally productive but globally unstable.

This formalization gives the paper a clean bridge from implementation to research method:

- judges create `E_i`
- correction prompts create `P_{i+1}`
- RACS scores the transition
- ablation studies tune the incentive structure behind that score

## Multi-Judge Evaluation Method

The multi-judge method asks several evaluator models to review the same proof independently.
Each judge returns a structured evaluation containing:

- overall verdict
- completeness score
- assumption-use score
- detailed feedback
- step-level error sets
- flagged steps for correction

The system then computes a single consensus output.

### Why multiple judges?

LLM judges can be noisy:

- one judge may miss a subtle gap
- one judge may over-penalize harmless exposition
- one judge may hallucinate an error
- one judge may be stricter or more lenient than others

Multiple judges reduce dependence on one evaluator's idiosyncrasies.
The goal is not to make the judges "prove" correctness, but to make the feedback signal more stable and auditable.

### How consensus is formed

The current implementation uses three main ideas:

1. **Error-set agreement**
   - Judges are compared by the proof steps they flag.
   - Agreement is measured using Jaccard similarity over step-level error sets.

2. **Outlier detection**
   - Judges whose scores deviate sharply from the group can be downweighted or treated as outliers.

3. **Reliability-weighted aggregation**
   - More reliable judges receive more influence in the final verdict and quality score.
   - Error sets are merged after considering valid judges.

In the implementation:

- consensus verdict is computed using ordinal verdict scores
- per-type error sets are majority-merged
- flagged steps are union-merged so the prover receives inclusive correction guidance

That last design choice is important:

- majority merging prevents one noisy judge from creating the official error set
- union merging of flagged steps avoids losing potentially useful repair instructions

## Judge Reliability Score

JRS estimates how trustworthy a judge is relative to the other judges in the same evaluation round.

The implemented form is:

```text
JRS_i = alpha * ESA_i - beta * |z_i|
```

where:

- `ESA_i` is the judge's mean Error Set Agreement with other judges.
- `z_i` is the judge's standardized deviation from the group score.
- `alpha` rewards agreement on error localization.
- `beta` penalizes outlier scoring behavior.

### Why JRS is trustable

JRS is not claiming that a judge is mathematically correct in an absolute sense.
It is a relative reliability measure inside an ensemble.

It is trustable for this use case because:

- it is based on observable agreement, not hidden model confidence
- it compares concrete step-level error sets, not just vague textual feedback
- it penalizes judges that score far away from the group
- it allows outlier handling before consensus is formed
- it produces an auditable numeric trace for each evaluation

In the paper, JRS should be described as a **consensus reliability heuristic**, not as a formal correctness guarantee.

## RACS Metric

The paper should use one name consistently: **Regression-Aware Correction Score (RACS)**.
This is the better name because the distinctive contribution is not merely scoring correction, but explicitly measuring regression-aware proof repair.

```text
RACS = (w_err * ERR + w_tfp * TFP) * (1 - w_rp_pen * RP)
```

### Components

`ERR`: Error Resolution Rate

- Measures how many previously identified error steps disappeared.
- Captures whether the correction actually fixed known problems.
- Formal definition:

```text
ERR = |E_prev \ E_curr| / |E_prev|
```

If `E_prev` is empty, ERR is treated as 1.0 because there were no known prior errors to fix.

`TFP`: Targeted Fix Precision

- Measures whether the steps explicitly flagged for correction were addressed.
- Captures instruction-following and feedback compliance.
- Formal definition:

```text
TFP = |F_flagged \ E_curr| / |F_flagged|
```

If no steps were flagged, TFP is treated as 1.0.

`RP`: Regression Penalty

- Measures whether new error steps appeared after correction.
- Captures non-monotonicity and proof instability.
- Formal definition:

```text
RP = min(1.0, |E_curr \ E_prev| / max(1, |E_prev|))
```

### Why implement this metric?

Formal verification is powerful, but expensive and often impractical for broad natural-language convergence proofs.
Many optimization proofs contain informal but standard reasoning patterns:

- smoothness descent lemmas
- convexity inequalities
- stochastic expectation steps
- telescoping sums
- rate extraction
- assumption matching

Fully formalizing each proof in Lean, Coq, or Isabelle would require substantial human engineering.
This project instead introduces an intermediate level:

- more granular than final pass/fail judging
- less expensive than full formal verification
- structured enough to track mathematical error transitions

RACS is useful because it turns proof correction into a measurable transition between two proof states.

### Useful Theoretical Properties

The paper can state these as metric properties before presenting results:

1. **Boundedness**
   - RACS is clipped to the unit interval: `0 <= RACS <= 1`.

2. **Perfect correction optimality**
   - A transition receives `RACS = 1` when all known errors are fixed, all targeted flagged steps are resolved, and no new errors are introduced.

3. **Regression monotonicity**
   - Holding ERR and TFP fixed, increasing RP decreases RACS.

4. **Mixed-transition sensitivity**
   - If a correction both fixes errors and introduces new ones, RACS does not collapse into a binary success/failure label.
   - This is useful because mixed transitions are common in long-form proof repair.

5. **Ceiling avoidance**
   - The multiplicative form allows perfect correction to reach 1.0 while still penalizing regressions.
   - This avoids scoring designs where the maximum possible score is accidentally capped below 1 because weights are allocated incorrectly.

## What RACS Evaluates

RACS does not evaluate a model's general intelligence in the abstract.
It evaluates the model's correction behavior in a guided proof-repair context.

It captures several abilities:

1. **Mathematical error repair**
   - Does the model fix previously identified mathematical errors?

2. **Instruction following**
   - Does the model address the exact steps the judge flagged?

3. **Reasoning stability**
   - Does the model avoid breaking previously correct parts of the proof?

4. **Feedback use**
   - Does the model convert external critique into a better proof?

5. **Hallucination reduction**
   - If hallucinated claims were flagged, does the corrected proof remove or justify them?

6. **Local-to-global proof discipline**
   - Does the model make local repairs without damaging the global convergence argument?

The metric is valid for this setting because the task is explicitly iterative and feedback-guided.
It would be less appropriate for evaluating a one-shot proof generator with no correction loop.

## Why Not Only Final Verdict?

A final verdict hides the trajectory.
Two systems may both end with a passing proof, but one may:

- fix all errors cleanly
- require one correction
- introduce no regressions

while another may:

- oscillate across proof versions
- fix one gap while creating another
- require multiple correction rounds

Final correctness cannot distinguish these behaviors.
RACS is designed to measure the correction process itself.

## How Metric Weights Are Obtained

The weights should be presented as calibrated rather than assumed.
The paper can explain the plan as:

1. Define a grid over `w_err`, `w_tfp`, and `w_rp_pen`.
2. Enforce `w_err + w_tfp = 1`.
3. Run the pipeline under each weight setting.
4. Compare resulting RACS values against an external quality target.
5. Select weights that best align with the target while preserving interpretability.

Possible quality targets:

- expert human proof-quality ratings
- reviewer rubric scores
- final structured judge verdicts
- manually labeled correction outcomes

The most paper-defensible version is human or expert rubric alignment.
If only judge-derived verdicts are used, the paper should say "judge-verdict proxy" rather than "human judgment."

### Why ablation is the right method

The weights represent design choices about correction incentives:

- high `w_err`: rewards fixing known errors
- high `w_tfp`: rewards following specific feedback
- high `w_rp_pen`: discourages new errors

Ablation is appropriate because these incentives may trade off.
For example, a very strong regression penalty may make the system conservative, while a weak penalty may allow exploratory fixes that solve deeper issues but risk instability.

The ablation should not merely find a numerically best point.
It should answer a scientific question:

> What incentive structure produces correction behavior most aligned with rigorous proof improvement?

### Correction Incentive Philosophies

The ablation section can present the weights as design philosophies:

| Configuration emphasis | Dominant incentive | Interpretation |
|---|---|---|
| High `w_err` | Aggressive error resolution | Prioritizes clearing known errors, even if the model makes broad edits. |
| High `w_tfp` | Targeted judge compliance | Prioritizes fixing exactly what the evaluator flagged. |
| High `w_rp_pen` | Conservative refinement | Prioritizes avoiding new errors and preserving stable proof regions. |

This framing makes the ablation scientifically meaningful.
The paper is not merely tuning hyperparameters; it is testing what kind of correction behavior should be rewarded.

## What a Strong A* Paper Should Emphasize

### 1. Clear problem formalization

Define:

- proof state at iteration `t`
- evaluator error set `E_t`
- flagged correction set `F_t`
- correction transition from `P_t` to `P_{t+1}`
- fixed errors, persistent errors, and regressions

This makes the paper more rigorous than a system description.

Good notation to reuse:

- proof trajectory: `P_0, P_1, ..., P_T`
- evaluator error trajectory: `E_0, E_1, ..., E_T`
- flagged-step trajectory: `F_0, F_1, ..., F_{T-1}`
- fixed set: `E_t \ E_{t+1}`
- regression set: `E_{t+1} \ E_t`
- persistent set: `E_t intersection E_{t+1}`

### 2. Explicit assumptions and scope

State clearly:

- proofs are natural-language / LaTeX mathematical proofs
- the system is not a replacement for formal proof assistants
- evaluator reliability is empirical and ensemble-based
- correctness is bounded by judge quality

This honesty increases trust.

### 3. Method before results

The paper should explain why each design decision exists:

- prover/judge separation
- deterministic evaluation
- step-level annotations
- structured JSON
- multi-judge consensus
- JRS weighting
- RACS transition scoring
- ablation-based calibration

### 4. Baselines to eventually include

For a complete paper, useful baselines would be:

- one-shot proof generation
- self-correction without external judge
- single-judge correction
- multi-judge majority vote without JRS
- final-verdict-only scoring
- RACS without regression penalty

### 5. Evaluation dimensions

A strong evaluation should separate:

- final proof quality
- correction quality
- regression frequency
- judge agreement
- number of iterations
- instruction-following quality
- cost and latency

This prevents the paper from reducing everything to one aggregate score.

### 6. Failure analysis

A good paper should include where the method fails:

- judges agree on a wrong criticism
- prover fixes symptoms but not the theorem
- proof becomes longer but not more rigorous
- corrections overfit to flagged steps
- assumptions are patched into the proof after the fact
- final verdict improves while mathematical validity remains uncertain

Failure analysis will make the work feel mature and research-grade.
